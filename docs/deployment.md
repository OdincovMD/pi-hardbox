# Установка и обновление

## Текущая работающая машина

Raspberry Pi 5, Debian/Raspberry Pi OS ARM64, systemd, NetworkManager,
nftables, iproute2, dnsmasq, curl, iw, kmod, Python 3. Для проектов нужен Docker
с Compose. Клоны исходников отделены от `/opt/pi-dashboard` и `/opt/hardbox-vpn`.
Упаковка репозитория не заменяет работающие файлы и не перезапускает службы.

Шаблоны используют пользователя/группу admin, интерфейсы eth0/wlan0,
подсеть 10.77.0.0/24 и домен сайта из dashboard.py. Приложения проектов
skin-cancer-ai/img2txt устанавливаются независимо. Для их мониторинга текущему
пользователю HTTP-сервера уже доступен Docker; это привилегия хоста,
а не дополнительная возможность, выдаваемая браузеру.

## Состав установки

| Исходники | Рабочее расположение |
|---|---|
| dashboard/*.py и dashboard/assets | /opt/pi-dashboard |
| gateway/manage.py, release.json | /opt/hardbox-vpn |
| deploy/systemd/*.service, *.timer | /etc/systemd/system |
| deploy/systemd/pi-dashboard.service.d | /etc/systemd/system/pi-dashboard.service.d |
| deploy/pam/pi-dashboard | /etc/pam.d/pi-dashboard |
| gateway/templates/firewall.nft, dnsmasq.conf | /etc/hardbox-vpn |
| приватный основной VPN/Wi-Fi JSON | /etc/hardbox-vpn, только root |
| приватный профиль AP | /etc/NetworkManager/system-connections/hardbox-vpn.nmconnection |
| Xray ARM64 | /usr/local/lib/hardbox-vpn/xray |

Метаданные загрузки и ожидаемый SHA256 Xray находятся в gateway/release.json.
Бинарник и скачанный архив в Git не включены. Сверяйте SHA256 архива перед
установкой; не меняйте существующую версию только ради копирования исходников.

## Первичная конфигурация на новой машине

Это отдельный шаг, не требующийся для работающей PI Hardbox. Генератор читает
VLESS URI и Wi-Fi-пароль с маскированным вводом, не принимает их в argv и
отказывается писать в Git checkout. Пример каталога вне репозитория:

```bash
python3 gateway/initialize_config.py --output /tmp/hardbox-private-config
```

Создаются xray.json, wifi.json и hardbox-vpn.nmconnection с правами 0600,
каталог 0700. Установите их как root в пути из таблицы и удалите временный
каталог после проверки. У генератора нет сетевых или systemd-действий.
Не подставляйте ключи в команды оболочки, имена файлов или документацию.

Первоначальная политика шаблона направляет весь допустимый трафик в VPN,
блокирует приватные назначения и оставляет diagnostics/DNS только в VPN.
Списки российских сервисов в шаблон не скопированы. После запуска контроллера
обновите их через защищённый интерфейс VPN: текущая версия загрузится из
upstream, а контроллер проверит и применит правила транзакционно.

На новой машине создайте /etc/hardbox-vpn и /var/lib/hardbox-vpn с root 0700.
Файлы основных JSON и профиля NetworkManager должны принадлежать root и иметь
права 0600; не копируйте их в каталог исходников. Импортируйте профиль
NetworkManager с autoconnect=false: включение AP принадлежит systemd.
Конкретные команды запуска firewall/AP меняют сеть и должны выполняться
только после проверки локального доступа к машине. Шлюз не устанавливает
общий VPN-маршрут для eth0 и не очищает общие таблицы Docker/Tailscale.

## Порядок служб

Firewall → основной Xray → AP → DHCP. Профиль AP не стартует сам при загрузке:
systemd включает его после защитных правил. Контроллер VPN использует основной
Xray, а сайт — локальные контроллеры PAM, вентилятора и VPN.
`hardbox-vpn-routing-refresh.timer` обновляет списки ежедневно.
Контроллер охлаждения конфликтует с прежним fancontrol, чтобы не было двух
одновременных писателей PWM. PAM-профиль использует common-auth/common-account;
на других дистрибутивах требуется соответствующая настройка PAM.

При установке на новую машину unit-файлы только копируются из deploy/systemd;
после daemon-reload включаются необходимые службы и timer. Не включайте AP до
готовности firewall. Публикация HTTP наружу выполняется отдельным HTTPS-туннелем
или reverse proxy; токены Tuna и конфиги внешнего туннеля не входят в проект.

## Обновление работающей установки

Сначала проверка исходников и Git, затем закрытая резервная копия изменяемых
рабочих файлов вне checkout. Копируйте только нужные исходники/юниты,
сохраняйте владельцев и права и перезапускайте только затронутые службы.
Обновление исходников не должно перезаписывать /etc/hardbox-vpn или /var/lib.
Смена VPN-ключа выполняется штатной транзакцией контроллера, а не Git deploy.

## Интеграция img2txt

Шаблоны img2txt.service и hardbox-img2txt-sync.service сохранены вместе с
img2txt_vpn_sync.py. Они предполагают существующий проект
/home/admin/python/img2txt, сеть skin-ai-network и собранный образ приложения.
В его игнорируемом корневом .env задаётся XRAY_CONFIG_PATH со значением
/etc/hardbox-vpn/img2txt/xray.json. Ключи LLM остаются в service/.env.

Первый запуск helper создаёт производный конфиг с root:65532 0640 в каталоге
root 0700, пересоздаёт прокси и запускает приложение. Контроллер сайта
вызывает helper после проверки основного VPN до фиксации обновления;
при ошибке возвращает прежний основной ключ и повторяет синхронизацию.
Неизменный применённый ключ не перезапускает контейнеры. Полный контракт
описан в docs/dashboard.md и в репозитории img2txt, infra/hardbox/README.md.

## Проверки после установки

HTTP /api/status, /api/vpn, /api/manage и /api/projects должны возвращать
свежие данные без секретов. Изменения без авторизации должны отклоняться.
Проверьте SSH/HTTP хоста, состояние проектов и Wi-Fi с отдельного устройства.
Настоящий reboot не является unit-тестом. Проверка отключения Xray и fail-closed
поведения временно прерывает клиентский VPN и выполняется отдельно.
